# 怎么向用户提问

> 用户是**产品负责人**，不是这个代码库的维护者。他关心的是「这局牌怎么打」，不是
> 「哪个类型放在哪个文件」。本文件规定提问的写法。违反它的代价是**问题被退回重问**，
> 而退回来的那一次往往要花掉一整轮。
> 实测来源：2026-11-18，用户连续两次退回技术化提问（C-24 毒药优先、C-27 同时达成），
> 第三次改写成牌桌语言后才拿到裁决。

---

## 1. 三条硬要求

### 1.1 先说「牌桌上会发生什么」

任何问题都要能翻译成一局牌里的具体场景：谁做了什么、然后会发生什么、玩家会看到什么。
**不要**从类型、文件、函数、缩写开始。

### 1.2 选项要写「在游戏里意味着什么」

「A 好人胜 / B 狼人胜」是合格的；「A 用 `night-wolf-priority` 条件 / B 复用 `all-gods-dead`」
是不合格的——后者要求用户先理解实现细节才能做产品决定。

每个选项给三样东西：**规则上等于什么**、**玩家会看到什么**、**代价是什么**。

### 1.3 技术标识只做锚点，不做内容

类型名、文件名、函数名、RFC 编号可以出现，但只能放在括号里当「这是哪一处的引子」，
例如：

> 狼在夜里聊天时，已经出局的狼还能不能看见聊天？（对应 RFC-005 §2.4）

**不要**要求用户理解「`isVisibleTo` 的 `diedSeq` 分支」之后才能回答。

---

## 2. 提问模板

```
## 现在的情况（一局牌里）
<2–3 句，谁做了什么，发生了什么>

## 需要你定的是
<一句话，用「能不能 / 判谁赢 / 要不要 / 放哪里」这种措辞>

## 选项
A. <规则上等于什么> —— <玩家会看到什么>；代价：<…>
B. <…>

## 我的建议
<哪个，一句话理由，也是牌桌语言>
```

**一次最多三个问题。** 超过三个说明还没想清楚，先自己收敛。

## 3. 反例（真实发生过的）

| 反例 | 问题 | 改写后 |
|---|---|---|
| 「`resolveNight` 对同一目标要按座位去重还是允许两条 `Death`？」 | 用户不知道 `resolveNight` 是什么，也不知道 `Death` 是什么 | 「女巫毒的人和狼刀的人是同一个。这个人算死一次还是两次？算谁杀的？」 |
| 「`AC-3` 对 `wolves` 事件的三句断言自相矛盾，选哪句？」 | 缩写 + 内部术语 | 「一个已经死掉的狼，还能不能看见狼队之后的聊天？」 |
| 「`ProjectedContext` 的类型归 RFC-006 还是 RFC-007？」 | 两个未定义的编号 + 一个未定义的类型 | 「AI 行动前会拿到一张'我现在知道什么'的清单。这份清单的格式谁定？」 |

---

## 4. 什么情况不需要问

- 纯实现选择（变量名、文件拆分、退避策略）——自己定，写进 `## Implementation Notes`；
- 有明确权威依据的（`RULES.md` 已裁决、`PRD` 已写死）——照做，别问；
- 用户已经裁决过、问题与选项都没变的——**直接沿用**，不要重复问。

问之前先自查这三条。都不符合才问。
