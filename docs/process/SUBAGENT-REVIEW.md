# 用 subagent 跑评审：调用方式与等待策略

> 本文件记录**怎么起一次评审**、**要等多久**、**拿到结论后怎么验证**。
> 评审的**输入规范**在 [`REVIEW-PROMPT.md`](REVIEW-PROMPT.md)；本文件只管**调用**。
> 实测数据来自 2026-11-18 的第一次真实使用（RFC-004 Round 1）。

---

## 1. 提示词：两行就够

subagent **不是**空白上下文：它能看到技能目录（`.dsh/skills/`，含 `review-rfc`）与
`AGENTS.md`（自动注入）。所以不需要在提示词里复述流程、约束或交付物——那是**重复**，
而且一旦与 `SKILL.md` 不一致，评审者就不知道该听谁的。

**标准写法**（实测有效）：

```
按 /review-rfc 004 执行（Round N）。
不要 git commit；变异探针改过的代码必须恢复。
```

- 第一行：**指针**。斜杠命令 = 技能名 + 参数，subagent 会自己加载对应 `SKILL.md`。
- 第二行：**项目约定**，技能正文里没有的两条（评审者不提交、探针必须回滚）。

### 只有这些情况才加内容

| 情况 | 加什么 | 为什么 |
|---|---|---|
| 要指定模型/推理强度 | 见 §5 的参数写法 | 不是提示词能表达的 |
| 上一轮有**未关闭的阻塞项** | 一行：「Round N-1 的 B1/B2 必须复核，不要重查已关闭项」 | 技能是按单轮写的，跨轮次的重点需要点名 |
| 目标不是标准评审（例如只查某个面向） | 一句话说明范围 | 技能默认全覆盖 |

**不要**把 `REVIEW-PROMPT.md` 的内容抄进提示词——评审者会自己读它（技能正文指向它）。

### 反例（我第一版就是这么写的，不要学）

- ❌ 「先读 docs/process/REVIEW-PROMPT.md …再读 AGENTS.md …」→ 技能自己会做
- ❌ 逐条列出「必须做的四件事」→ 与技能正文重复，且容易漂移
- ❌ 复述「只改文档、不改 src」→ 技能与 AGENTS.md 都有

## 2. 等待：**不要用 10 分钟当上限**

| 任务 | 实测耗时 |
|---|---|
| 完整评审（六条门禁 + 10 条变异探针 + fuzz + 读代码） | **约 20 分钟** |
| 只读小探针（读几个文件、回答两三个问题） | **1–3 分钟** |

我第一次按 10 分钟等，超时了——**超时不等于失败**，只是"还在跑"。

### 推荐节奏

```
起 subagent
  → wait_agent(900000)          # 15 分钟，覆盖绝大多数完整评审
     ├─ timedOut: false → 拿结果
     └─ timedOut: true  → 再 wait_agent(900000)，最多三轮
```

- **不要** kill 掉重开：kill 会丢弃已完成的探针，而且新起的 subagent 不知道前一个做到哪。
- 想在等待期间判断它是否还活着，用**只读**信号：`git status --porcelain`（探针期间会有改动）、
  `reviews/REVIEW-RFC-<id>.md` 是否出现。**不要**为了"看看进度"去改文件——会与它冲突。

## 3. 拿到结论后：先验证据，再动手

评审者的结论是**待核实的输入**，不是终审。按 §4 的顺序抽查：

1. **门禁输出**是不是它自己跑的（贴了真实输出 vs 只说"全绿"）；
2. **阻塞项能不能复现**：自己跑一遍它给的复现路径（RFC-004 的 C-31 我就是这么确认的）；
3. **探针结果是否双向**：它说"改回去会红"，至少挑一条自己试；
4. **它自己承认的"没验证"部分**——那些地方要当作未验证，而不是"应该没问题"。

第一次使用（RFC-004 Round 1）的实际表现，可作参考基线：六条门禁实跑、10 条探针
（其中 3 条**不红**并如实报告）、200 种子 fuzz、两个只读探针；找到 2 个不在 AC 覆盖面
上的阻塞项，其中一个是实现者自己漏掉的信息泄漏。

## 4. 已知会失败的地方

| 现象 | 原因 | 处理 |
|---|---|---|
| 直接传 `reasoning_effort` 报错「requires both `provider` and `model`」 | 该字段不能单独使用 | 三个一起传：`provider` + `model` + `reasoning_effort`（见 §5） |
| 评审者不加载技能，自己发明评审流程 | 提示词没给指针 | 用 §1 的标准写法；它看到斜杠命令会去找技能 |
| 它在 `git status` 里留下探针改动 | 忘了回滚 | 提示词第二行就是这条约定；拿到结论后先看 `git status` |
| 结论全是"通过"，没有一条 finding | 可能没做探针 | 追问「你改了哪几处代码、哪条测试变红」；答不出就重跑 |

## 5. 参数写法（本仓库当前只有一种模型）

```ts
subagent({
  provider: 'deepseek-account',
  model: 'deepseek-flash',
  reasoning_effort: 'max',      // 评审用 max；实现会话是默认档 high
  description: 'RFC-004 Round 2 review',
  prompt: '按 /review-rfc 004 执行（Round 2）。\n不要 git commit；变异探针改过的代码必须恢复。',
})
```

`reasoning_effort` 与实现会话不同档，是这条流程**唯一**的独立性来源（同模型，见
`REVIEW-PROMPT.md` §8.1 的已知局限）。将来接入第二个模型时，改用与实现者不同的那个。

---

## 6. 什么时候**不要**用 subagent

- 需求裁决、规则冲突取舍 → 那是用户的事，不是评审者的事；
- 修复阶段 → subagent 只评审，修由实现会话做（它在提示词里被禁止改 `src/`）；
- 需要看到中间过程的调试 → subagent 只回最终结论，中间步骤看不到。
