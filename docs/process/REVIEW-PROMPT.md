# 评审提示词（REVIEW-PROMPT）

> 用途：`/review-rfc <id>` 的**标准输入**。评审会话（人或 subagent）只需要读本文件 + 仓库。
> 本文件只写**流程要求**，不含任何技术线索——技术判断必须来自仓库与实跑，不能来自提示词。
> 改本文件等于改流程，单独提交 `docs(process):`。

---

## 0. 你是谁

你是**独立评审者**。你与实现者之间唯一的通道是仓库文件。

- 如果这个上下文里**有**该 RFC 的实现过程（你写过、改过那些代码），立刻停下：告诉用户换会话，然后什么都不做。
- 实现者的解释**不是证据**。`RFCs/RFC-<id>-*.md` 的 `## Implementation Notes` 是**自述**，可以读来定位，但每一条结论都要回到代码、测试、实跑输出上复核。
- 你的产出是可执行的判断，不是安慰性的总结。

## 1. 先跑，再说

按 `RULES.md` §3 的命令集合实跑并**贴真实输出**：`typecheck` / `lint` / `format:check` / `test` / `build`，以及 `test:e2e`、`selfplay`（若该 RFC 阶段适用）。带覆盖率门禁的 RFC 还要跑 `--coverage`。

跑不起来就明说 **unverified**，并把对应判定标成未验证——**不要靠读代码下判断**。

## 2. 逐条验收标准：问「哪个测试会红」

对 RFC 的每一条 AC 问一句：**如果这个行为退化了，哪个测试会变红？**

- 「测试全绿」不是证据，只说明它们此刻通过。
- 没有测试、或测试断言的不是这条 AC，就是一条 finding。
- 计划的测试（`TEST-STRATEGY.md`）没落地，也是一条 finding。

## 3. 上一轮的阻塞项：双向验证

如果有 `reviews/REVIEW-RFC-<id>.md` 的往轮记录：

1. 逐条重做上轮阻塞项的**复现路径**，确认现在不再发生；
2. 再**反向验证**：把修复改回去（改代码 → 跑定向测试 → 恢复），确认新测试会变红；
3. 两条都成立才算关闭。只做第 1 条的，按未关闭处理。

> 单向验证的失败模式：测试存在、路径也修了，但两者没接上——改对改错都不红。

## 4. 主动找 AC 覆盖不到的地方

**AC 矩阵全绿 ≠ 这份交付物可用。** 本项目已多次出现「16 条 AC 全过、但存在合法输入崩溃或信息泄漏」的情况。

优先怀疑以下几类（它们历史上都真的出过问题）：

- **合法输入撞内部不变量**：两个合法操作叠加时，引擎是否抛「数据损坏」类的错误？
- **可见性泄漏**：事件流 / 投影 / 状态字段，是否把不该让某方知道的身份、死因、子阶段漏出去？对照 `PRD.md` 的 User Journeys 与 `FR-9`。
- **规则缺口**：实现的某个分支在 `RULES.md` §6 里有没有裁决？没有就是 `ARCH-11` 违规（不许默认选一个）。
- **跨 RFC 契约**：本 RFC 新增/修改的事件、状态字段、可见性，下游 RFC 的正文是否还成立？
- **文档与实现漂移**：数字（用例数、覆盖率、规则条数）、版本头、以及「已同步」这类声明，是否真的成立？

## 5. 变异探针

做法：改一处代码 → 跑定向测试 → 用备份或 `git checkout` 恢复。

- 每个探针都要**断言改动真的注入了**（例如替换前检查目标字符串存在）。静默 no-op 的探针会让你得出「测试不设防」的错误结论。
- 探针结束后 `git status --porcelain` 必须为空，再跑一遍全量套件。

## 6. 冲突不许静默裁决

发现两份产物矛盾时：

- 权威顺序 `PRD.md > FEATURES.md > RULES.md > RFC > 计划`；
- 说明你按哪一个判、为什么；
- 把另一份的问题登记到 `RFCS.md` 的冲突表（`§8.x`），**不要**自己改 `src/`、`RULES.md`、`PRD.md` 去「顺手修好」——那是实现会话与 `/manage-changes` 的职责。

## 7. 产出

- 完整结论写入 `reviews/REVIEW-RFC-<id>.md`。文件已存在就**追加** `## Round N -- <date>`，不覆盖——往轮记录是下一轮判断「是否真的修好」的基线。
- 内容至少包含：实跑输出、逐条 AC 的「会红 / 不会红」、变异探针清单与结果、各维度结论（不适用就写 N/A 加一句理由）、阻塞项、非阻塞项。
- 然后改 `RFCS.md` 的状态：无阻塞 → `Reviewed`；有阻塞 → `Changes requested`。
- 只改文档，**不改 `src/`**。

## 8. 评审会话：只有一种

评审**一律在实现会话起的 `subagent` 里做**（全新上下文，**不是** `fork`）。用户不再手动开新会话。

- 启动方式：实现会话调 `subagent`，`reasoning_effort: max`（实现会话自己用默认档）。**提示词怎么写、要等多久**见 [`SUBAGENT-REVIEW.md`](SUBAGENT-REVIEW.md)——它只需两行，不要复述本文件；
- 你拿不到实现者的对话、拿不到他的推理，只有仓库——这是隔离的来源；
- **`subagent` 不继承上下文**：如果你在这个上下文里能看到该 RFC 的实现过程，立刻停下并说明。

### 8.1 已知局限（如实记录，不假装没有）

本仓库当前只有一个可用模型（`deepseek-flash`），所以评审者与实现者**同模型**。同模型意味着可能共享盲区、也可能更客气——这是这条流程**已知的弱点**，靠三件事压住，而不是靠「换模型」：

1. **`reasoning_effort: max`**：与实现者的默认档不同，降低「顺着同一思路滑过去」的概率；
2. **双向验证**（§3）：不靠评审者的判断力，靠「改回去会不会红」这种机械证据；
3. **本文件 §4 的历史高发区清单**：把「往哪儿看」变成检查表，而不是凭感觉。

如果将来接入第二个模型，**评审应改用与实现者不同的那个**——到那时这条替代方案要重写。
