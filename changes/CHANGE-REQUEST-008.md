# 变更请求 008 · 死亡公告不得携带死因顺序（C-31）与 F5 AC-4 的旧文字（C-32）

> 提出日期：2026-11-18
> 提出人：RFC-004 Round 1 评审（C-31 阻塞 RFC-004；C-32 非阻塞但阻塞后续规格）
> 评估基线：`RFCs/RFC-004` §2.1 / AC-2~4、`PRD.md` FR-9、`RULES.md` §6（RUL-2 / RUL-12）、`FEATURES.md` F5 / F7
> 决策状态：**已裁决并落地**（C-31 由用户选择「按号码报死者」；C-32 为 CR-002 既有裁决的文本同步）

---

## 0. 总体判断

两件事都不是新需求，是**规格写错了 / 落后了**。

### C-31：公开的死亡公告把死因写进了顺序

RFC-004 §2.1 规定 `DAY_STARTED.diedLastNight` 按「死亡结算顺序」排列，而结算顺序固定是**狼刀先、毒药后**（`src/engine/resolve/deaths.ts`）。这条 payload 是 `public` 的，于是：

```
DAY_STARTED public {"day":1,"diedLastNight":[6,1],"speechStartSeat":7}
```

全桌都能读出「6 号被刀、1 号被毒」。更麻烦的是发言起点挂在同一个顺序上（「第一个死者的下一位」），**同一个泄漏走了两条路**。

**真实牌桌不是这么报的。** 通行做法是按**号码**报死者（或者只说「死两个人」），目的正是让人分不清谁被刀谁被毒（[知乎·结算问题](https://zhuanlan.zhihu.com/p/625739586)：「不分先后的，一般按照号码顺序报死亡信息，目的就是为了让大家分不清谁是被刀谁是被毒的」）。

泄漏的实际后果：

| 谁 | 拿到什么 | 后果 |
|---|---|---|
| 好人 | 毒用在哪 | 等于确认女巫这一夜开了毒 |
| wolf | 女巫用的是毒不是解药 | **推算出解药还在**，下一夜敢刀她 |
| AI（RFC-007 会把 public 事件喂进去） | 同上的全部 | 直接违反 `FR-9`「AI 只能使用自己有权知道的信息」 |
| 全体 | 单死时判断「这是刀口还是毒杀」 | 本应不可能 |

RFC-003 的 D-3 专门把夜间 `PLAYER_DIED` 设为 `server` 就是为了藏死因 —— 这条公开 payload 又把它漏了回去。

### C-32：`FEATURES.md` 仍在说「重投可以弃权」

`FEATURES.md` F5 AC-4 写「平票重投…选项集为并列者 **+ 弃权**」，而 `RULES.md` RUL-2（`CHANGE-REQUEST-002` 时期由用户裁决）写「**不能弃权**」。RFC-004 AC-8 与实现按 RUL-2 走。

权威顺序里 `FEATURES > RULES`，所以这不是「RULES 覆盖 FEATURES」，而是**FEATURES 的那句写于裁决之前、没有同步**。

| 规则 | Y-1 | Y-2 |
|---|---|---|
| **RUL-2**（重投不能弃权） | 不涉及 | **满足**（改完 FEATURES 与它一致） |

| **RUL-1**（判定时机） | 不涉及 | 不涉及 |
| **FR-9**（AI 不得使用无权知道的信息） | **满足**：公告只含「谁死了」 | 不涉及 |
| **FR-6**（发言起点可复现） | 满足：新规则同样确定、无需随机 | 不涉及 |

与既有 CR：

- **CR-002** 裁决了重投不能弃权（Y-2 只是把文本补上）；同一份裁决也移除了平局。
- **CR-006 / RUL-12** 定了夜间同时达成的判法（Y-1 不改它）。
- **CR-005 / RUL-11** 定了同目标既被刀又被毒时的死因（Y-1 不改它，但**公告不再暴露这个死因**，方向一致）。

## 3. 逐处改动

### 3.1 `RFCs/RFC-004` §2.1

**现在**：

> `diedLastNight: SeatId[]; // 按死亡结算顺序`
> 规则：若 `diedLastNight` 非空，取其中**结算顺序第一位**的下一位存活席位

**改为**：

> `diedLastNight: SeatId[]; // **按座位升序**（不得携带死因顺序）`
> 规则：若 `diedLastNight` 非空，取其中**座位最小者**的下一位存活席位；若为空，用 `state.rng` 在存活席位中抽一个。

并补一段理由：报死者的顺序会暴露死因（狼刀先、毒药后），而真实牌桌按号码报正是为了藏它；`speechStartSeat` 同理不能依赖结算顺序。

### 3.2 `RFCs/RFC-004` AC-2 / AC-3 / AC-4

- AC-2：「结算顺序第一位死者的下一位」→「**座位最小的死者**的下一位存活席位」
- AC-3 / AC-4 不变（无死者时抽签；起点是死者则跳过）
- 新增 AC：**公开的 `DAY_STARTED` 不得泄漏死因**——两个死者时，payload 的顺序与「谁被刀」无关（用两条相反场景的用例断言同一个顺序）

### 3.3 代码

| 文件 | 改动 |
|---|---|
| `src/engine/phases/day.ts` | `speechStartOf`：不取 `pendingDeaths[0]`，取 `Math.min(...deaths)`；`dayAnnounceEntry` 对 `diedLastNight` 排序 |
| `src/engine/apply.ts` | `pendingDeaths` 仍按结算顺序累积（它服务于「谁死了」的集合语义），但**输出时**排序 |
| 测试 | `day.test.ts` 的 AC-2 断言改为「座位最小死者的下一位」；新增「两种死因顺序得到同一个公告顺序」的用例 |

### 3.4 `FEATURES.md` F5 AC-4

「选项集为并列者 **+ 弃权**」→「选项集**仅为并列者本身**，不能弃权（RUL-2）」。

## 4. 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 保留结算顺序，把 `DAY_STARTED` 改为 `server` | 天亮公告本来就是全场可见的；藏掉它等于玩家不知道昨晚死了谁 |
| 公告不带顺序、但发言起点仍按结算顺序 | 起点会独立泄漏「谁是第一个死者」，等于泄漏没修 |
| 发言起点改用抽签 | 会话多一次随机、且难向玩家解释；真实规则按号码已经够用 |
| 把 `diedLastNight` 改成无序集合（`Set`） | 状态与事件必须可 JSON 往返（RFC-002 AC-3），数组更合适；排序即达标 |

## 5. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 排序后「谁先死」的信息在内部也丢了 | 将来若要「按死因区分公告」会缺数据 | 结算顺序仍保留在 `pendingDeaths` 的**内部**顺序与 `PLAYER_DIED` 的 `seq` 里，只是不进公开 payload |
| 只改公告忘了起点 | 泄漏仍在 | 两处都改，并加「同时验两条路径」的用例 |
| RFC-004 已 `Changes requested` | 改完要重跑评审 | 正常流程：修完 → `Implemented` → Round 2 |
