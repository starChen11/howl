> 提出日期：2026-11-17
> 提出人：用户
> 评估基线：`PRD.md` v0.3（53 条需求：36 FR + 17 NFR）、`PRD-REVIEW.md`（21 项发现）
> 当前阶段：**阶段 2 完成、阶段 3 未开始**。`FEATURES.md` / `RULES.md` / `RFCS.md` / `RFCs/` / `TEST-STRATEGY.md` / 代码**均不存在**
> 决策状态：**6 项全部已接受**（2026-11-17），已落地到 `PRD.md` v0.4 与同一提交

## 0. 总体判断

**这是一个"最好时机"的需求变化，但不是"零成本"的。**

好时机：项目卡在阶段 2 与阶段 3 之间，下游产物一份都还没生成。没有 FEATURES 要改、没有 RULES 要推翻、没有 RFC 要重编号、没有代码要返工。晚一个阶段（RULES 定稿后）成本约 ×3，晚到阶段 7 之后成本约 ×10。

不是零成本：用户提出的玩法与 v1 的三条既有决策存在**结构性张力**，不是"加个模块"那么简单：

| 张力 | 具体冲突 |
|---|---|
| 元层需要跨对局状态 | 与 **NFR-4**（不要求服务重启后仍在）、**NFR-17**（每局状态结束后必须可被释放）、Won't 表「账号、存档、历史战绩」直接冲突 |
| 元层是留存机制 | 与 **D10**（v1 成功标准 = 能展示，明确**不**追求留存）方向相反 |
| 遗物 = 修改规则 | 与 **NFR-2**（纯函数状态机）需要额外的效果插入点，否则将来加遗物要重写全部结算逻辑 |

结论：**玩法本身推迟到未来版本（C1），但为它预留的 4 个扩展点 + 随机种子应该在 v1 就位（C2–C6）**。这五项在 v1 里几乎零额外成本——v1 本来就为了测试可复现、刷新恢复、再来一局要做这些事；但事后补要重写结算层与状态层。

**关键判断依据**：不是"将来可能有用所以先做着"，而是"这五项里没有一项是只为元层服务的"。见 §3 逐条的成本论证。

| ID | 变更 | 类型 | 规模 | 优先级（v1） | 建议处置 |

## 2. 冲突检查（必须先看这一节）

### 2.1 与 RULES.md 的冲突

**不适用**：`RULES.md` 尚未生成，不存在可被违反的规则。本变更应在阶段 4 生成 RULES.md 时被纳入考虑，建议届时新增一条架构规则（如「结算必须通过效果序列，禁止在结算分支里内联效果」）。

### 2.2 与 Decisions 的冲突

| 决策 | 是否被推翻 | 说明 |
|---|---|---|
| **D10**（v1 成功标准 = 能向朋友展示；明确不追求留存） | **方向相反，但不推翻** | 元层是留存机制。v1 仍不追求留存，因此 C1 推迟是正确的；但必须承认"未来方向包含留存"。若将来实施 C1，D10 需要走变更流程重新评估 |
| **D1**（单机优先；单机是联机超集） | **被强化** | Roguelike 元层天然是单人体验，不需要凑人。它进一步支持了 D1 的选型 |
| **D3**（v1 固定 9 人标准局） | 无冲突 | 元层的随机路线不要求 v1 支持多板子；FR-28（多套板子）已是 Could Have |
| **D16**（玩家身份随机） | 潜在张力（未来） | Roguelike 通常给玩家更多"控制感"（选遗物 = 选构筑）。未来可能有人要求"用道具换身份"。**v1 不做，记为未来议题** |
| **D17**（AI 严格视野，绝不作弊） | **需要延伸，不能削弱** | 一旦有遗物改变信息获取（如"查看看守者日志"），AI 也必须知道这些机制才能合理应对。**这条底线对未来版本同样成立**，不得因为道具系统而放宽 |
| **D25**（LLM 成本不设上限） | 无冲突 | 但元层会让单次游玩包含多局，长期成本会上升，未来需重新测算 |
| Won't 表「账号、存档、历史战绩、排行榜」 | **理由部分失效** | 原文理由是"v1 不追求留存，只追求展示"。元层正是留存，因此这条从"永远不做"变成"v1 不做、未来以存储接口引入" |
| Won't 表「中途存档 / 读档」 | 无冲突 | 指单局内存档；元层的跨局状态是另一回事，由 C5 覆盖 |

### 2.3 与 NFR 的冲突

| NFR | 冲突 | 处置 |
|---|---|---|
| **NFR-4**（不要求跨设备、不要求服务重启后仍在） | 元层需要跨重启 | **不修改 NFR-4 的行为**。C5 只加"存储接口"这一层边界，v1 仍用内存实现。未来替换实现即可，不动调用方 |
| **NFR-17**（每局对局状态结束后必须可被释放） | 元层需要部分状态**不**被释放 | C5 明确区分「对局状态」（可释放）与「元状态」（走存储接口）。NFR-17 保持不变，只是适用对象收窄为对局状态 |
| **NFR-2**（纯函数状态机、可序列化重放） | 遗物 = 修改结算，需要插入点 | C3 提供；且 C3 的设计必须不破坏纯函数性（效果也是状态转移的一部分） |
| **NFR-12**（重跑事件流得到相同公开信息） | 无冲突 | C6 的种子使其更可测 |

### 2.4 与产品差异点的冲突

**无冲突，方向一致。** 差异点是"打开就能玩、AI 不作弊、文字局"。Roguelike 元层加的是"每次玩不一样"，与三条差异点都不冲突，反而补上了 v1 缺少的长期动机。

## 3. 逐项评估

### C1 · Roguelike 元层（New Feature / Large / Won't have）

**内容**：在狼人杀之外套一层「杀戮尖塔」式的进度结构——随机路线节点（战斗、商店、事件、休整等）、遗物、可购买的狼人杀主题道具；不保留卡牌战斗，每个节点落到一局狼人杀上。细节由用户在未来版本定义。

**不实现于 v1 的理由**（不是"以后再说"，而是三条具体理由）：
1. 用户明确说"可以放到以后版本再详细定"——规格未定就写进 PRD 会把猜测变成最高权威（PRD 自身的规则）。
2. 元层的核心是留存，而 v1 的成功标准（D10）与不做清单都明确排斥留存机制。v1 做它等于同时做两个产品。
3. 元层会引入余额/货币/解锁/物品平衡，这些都需要玩家基数与数据才能调，v1 没有。

**登记方式**：不写成 FR（写了就会被 trace-check 计入 v1 需求覆盖），而是写进 PRD 新增的「后续版本候选」节，并加入已有的「已推迟到后续 RFC」清单。

**风险**：只记录不实现 → 一年后没人记得为什么留这几个口子。**缓解**：在 PRD 里写明"留口子的原因"并链接到本文件。

---

### C2 · 对局边界抽象（Technical / Small / Must）

**现状问题**：PRD 的隐含模型是「一个会话 = 一局」。FR-25（刷新恢复）、NFR-4（会话关联）都按这个写。元层要求「一个 run 包含多局」，届时"会话 = 一局"的假设会散落在状态管理、路由、恢复逻辑里。

**变更内容**：会话与对局改为**一对多**。数据模型必须能表达"某会话下有 N 局，含已完成的历史局"，且「一局」可被外部创建/推进/结束。v1 的 UI 仍只暴露「再来一局」。

**成本论证（为什么不是过度设计）**：v1 已经需要这件事——
- FR-13「再来一局」要求同一会话反复开局
- FR-34 headless 要求批量跑多局
- NFR-17 要求旧对局可释放

也就是说 **v1 本来就必须支持"会话 > 1 局"**，只是 PRD 没写清。C2 主要是把这个隐含要求显式化，成本接近零。

---

### C3 · 结算的显式效果序列与插入点（Technical / Medium / Must）

**这是五项里唯一有真实设计成本的一项。**

**现状问题**：NFR-2 要求纯函数状态机。若 v1 把结算逻辑写成"if 女巫有解药 then ... else if 猎人被毒 then ..."这种内联分支，未来任何遗物（"你的第一次被投票无效"、"你被刀时有一半概率被救"）都要插进这些分支里——每加一个遗物改一次核心结算，纯函数性和可测性都会被破坏。

**变更内容**：结算必须表示为**显式的效果序列**：引擎在每个结算点（夜间行动、投票、出局、胜负判定）产出一组带来源标记的效果记录，按确定顺序应用。v1 **不注册任何额外效果来源**，但必须留下可注册的位置，并有测试证明插入点真的能改变结算结果（用一个假效果验证）。

**成本论证**：
- 现在做的成本：把已经要写的结算代码组织成"产出效果列表 → 依次应用"的形状，是写法选择，不是额外功能。
- 事后补的成本：重写结算层，且要重新验证所有已通过评审的 RFC。
- **但也要承认**：如果 v1 的结算逻辑本来就很短（9 人局、4 个角色），内联写法也能跑，C3 的收益要在 M4（规则引擎 RFC）才能真正体现。因此它标 Must 而不是 Should，理由是"改造成本远高于写对成本"，不是"现在就有用"。

---

### C4 · 效果来源标记（Technical / Small / Should）

**现状问题**：v1 的所有效果都来自角色技能。数据模型若把"效果"和"角色"绑死，遗物产生的效果无处安放。

**变更内容**：对局状态中任何效果（击杀、免疫、信息获取）都记录其来源（角色 / 系统 / 未来扩展）。**不**要求 v1 实现非角色效果。

**成本论证**：与 C3 同批做几乎零成本（效果记录本来就要建）；单独事后补要改事件流格式，而事件流格式已被 FR-12 复盘、NFR-5 序号、NFR-12 重放引用。

---

### C5 · 元状态存储边界（Technical / Medium / Should）

**现状问题**：NFR-4 与 NFR-17 把"状态只活在对局/会话内、结束后可释放"写成了要求。元层需要跨对局、跨重启的状态。若 v1 把状态访问散落在各处，未来必须全局搜索替换。

**变更内容**：所有**跨对局**状态的读写经过单一存储接口；v1 用进程内存实现；接口不得暴露"仅内存"的假设（例如不得返回可直接修改的内部对象，应返回副本或不可变视图）。

**明确边界**（防止越界）：
- **不改变** NFR-4 的行为：v1 仍然刷新可恢复、重启即丢失
- **不改变** NFR-17 的行为：对局状态仍然可释放
- **不引入**账号、数据库、迁移
- 元层状态在 v1 里**根本不存在**，只有一个空接口和内存实现

**成本论证**：这是五项里最接近"为未来而做"的一项，因此标 **Should** 而非 Must。它值得做，因为"状态访问方式"是一个贯穿全项目的约定，事后补的代价随代码量线性增长；但不做它，v1 也能正常运行。

**替代方案（若拒绝 C5）**：把 NFR-17 的状态释放集中写在一个模块里，未来只改那一个模块。成本略高，但可接受。

---

### C6 · 随机种子（Technical / Small / Must）

**现状问题**：PRD 已经在两处隐含依赖种子——FR-16 的验收要求"固定种子与预设状态的定向对局"，FR-34 要求 headless "按指定局数与种子"批量跑。但**没有任何 NFR 明确要求种子机制**。这意味着它可能在实现时被当作测试脚手架而不是产品能力。

**变更内容**：新增 NFR——对局创建必须接受并记录随机种子；相同种子 + 相同玩家输入序列必须产出相同的公开信息序列。

**成本论证**：FR-16 与 FR-34 的验收**已经依赖它**，不补这条 NFR，那两个 FR 的验收方式就是悬空的。所以 C6 不是为元层做的，是补 v1 自己的漏洞；元层只是顺手受益。

## 4. 实施策略

| 变更 | 处置 | 落点 |
|---|---|---|
| C1 | 未来版本，v1 不实现 | PRD 新增「后续版本候选」节 + 扩写「已推迟到后续 RFC」清单；**不写 FR** |

**实施顺序建议**（供阶段 5 拆 RFC 参考）：
1. C2 + C6 进「规则引擎 / 状态机」那个 RFC（它们本就是状态机的一部分）

3. C5 可以进状态机 RFC，也可以进基础设施 RFC；建议前者，避免为它单开 RFC

**测试策略**：`TEST-STRATEGY.md` 尚未生成，因此不需要追溯修改；阶段 6 生成时须为 FR-37 ~ FR-40 与 NFR-18 各写测试小节。特别地，C3 的验收应包含一个"假效果插入点"的测试，否则它只是文档承诺。

## 7. 风险评估

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| **过度设计**：为一个还没想清楚的玩法改架构 | 中 | v1 变慢、变量变复杂 | 严格限定为 5 个扩展点，且每项都给出"v1 本来就需要"的成本论证；拒绝任何"顺便把遗物数据结构也建好"的提议 |
| **扩展点无人使用**：留了口子但实现时绕开 | 中 | 白留 | C3 的验收要求"用假效果证明插入点可用"；否则它只是注释 |
| **C1 的细节漂移**：未来真的动手时发现想做的和当初留的口子对不上 | 中 | 部分返工 | 本文件记录当时的口子清单与理由，未来实施时先读它 |
| **NFR-4 / NFR-17 被悄悄放宽** | 低 | v1 引入持久化、复杂度失控 | C5 明确**不改变**这两条的行为；PRD 措辞里写死"v1 仍为内存" |
| **元层与 AI 严格视野（D17）冲突** | 低（未来） | 道具若泄露隐藏信息会破坏信任底线 | 在 PRD 的 D17 理由中补一句：未来任何道具机制同样受严格视野约束 |
| **成本上升** | 中（未来） | 一个 run 含多局，token 消耗成倍 | 未来实施 C1 时重新测算；v1 不受影响 |

**不实施 C2–C6 的业务风险**：v1 照常能交付、能演示。代价出现在未来——加元层时要么重写结算与状态层，要么把元层做成外挂式（体验割裂）。属于**技术债**，不是**业务阻塞**。

## 8. 被否决的替代方案

| 替代方案 | 为什么否决 |

### 9.2 为什么没有触发「Spec changed」

`/manage-changes` 的规则要求：**验收标准变了的 RFC，若已 Implemented / Reviewed 则状态改 Spec changed**。

本次**没有触发**，因为项目当前处于阶段 2 与阶段 3 之间：
- `RFCS.md` 与 `RFCs/` 不存在 → 没有 RFC 的状态需要改
- `reviews/` 不存在 → 没有已评审的实现
- 没有任何代码 → 没有已实现的行为需要重新验证

这是本次变更成本最低的根本原因，也意味着**不存在"已评审的代码对应一个已不存在的规格"这类负债**。
