# CHANGE-REQUEST-011 · 狼刀改为狼队投票决定

**日期**：2026-11-20
**提出者**：用户（试玩反馈）
**状态**：**Accepted（2026-11-20）**

---

## 0. 一句话

现在「狼今晚刀谁」由**第一个出手的狼**决定；用户要求改成**狼队投票**，平票重投——因为将来真人联机时，三个狼都是真人，不能把共同决定权交给一个人。

## 1. 变更分类

| 维度 | 结论 |
|---|---|
| 类型 | **Feature Modification**（既有规则流程的改变） |
| 规模 | **Medium**（引擎相位 + 事件契约 + AI + UI + 测试 + 文档） |
| 优先级 | **Must have**（PRD G4 已声明为联机留位；决定权归属是规则公平性问题） |

## 2. 冲突检查（先做）

| 检查对象 | 结论 |
|---|---|
| `RULES.md` | **没有**任何一条裁决「狼队如何达成击杀决定」。RUL-1 / RUL-11 / RUL-12 只涉及结算顺序与死因，**不受影响**。所以这不是违反规则，而是规则**缺失**——需要新增一条（拟 **RUL-13**） |
| `PRD.md` 决策 / 不做清单 | 联机对战 v1 不做（PRD §不做清单），但 **G4「架构上为联机留出扩展位」** 是既定目标。当前「第一个出手者决定」把共同决策压成单人决策，与 G4 的精神冲突。**不是**推翻 v1 范围 |
| 产品差异点 | 差异点是「一个人也能玩」，本变更不触碰；它让单机流程更接近真实牌桌，反而强化「AI 与玩家地位对等」（FR-10） |
| 与既有 RFC 的契约 | RFC-001 §2.3 的动作契约里 `WOLF_KILL` 是单一动作；RFC-003 §2.3 的相位表把 `NIGHT_WOLVES` 定义为「提交一次 `WOLF_KILL`」。本变更要**改这两处契约**，因此 RFC-001 / RFC-003 / RFC-010（流）需要 `Spec changed` |

## 3. 影响分析

### 3.1 规则（RULES.md，拟新增 RUL-13）

- 狼队击杀决策 = **每名存活狼一票**，只能投存活且非狼的席位；平票 → **只对并列者重投**（弃权与投他人无效，RUL-2 的同构做法）。
- 重投仍平票怎么办：**待用户裁定**（见 §6 开放问题）。
- 死狼不投票；狼全灭的瞬间由胜负判定先结束（RUL-1 不变）。

### 3.2 引擎（src/engine）

| 文件 | 改动 |
|---|---|
| `phases/night.ts` | `NIGHT_WOLVES` 从「接收 `WOLF_KILL`」改为「接收 `WOLF_VOTE`」；全员投完且无并列 → 产出 `WOLF_KILL_CHOSEN` 并推进；并列 → 进入 `NIGHT_WOLF_RUNOFF`（新相位） |
| `phases/night.ts` | 重投仍是 `WOLF_VOTE`，候选只含并列者；再次平票走 §6 的裁定 |
| `shared/actions.ts` | 新增 `WOLF_VOTE { seat, target }`；`WOLF_KILL` 是否保留：**保留为内部效果**（不再由玩家提交），或删除并让引擎直接产出 `WOLF_KILL_CHOSEN` |
| `shared/events.ts` / `schemas.ts` | 新增 `WOLF_VOTE_CAST`（`visibleTo: 'wolves'`）与 `WOLF_VOTE_REVEALED`（狼队可见，含票型）；`WOLF_KILL_CHOSEN` 保留 |
| `project/targets.ts` | `pending: 'kill'` 的合法目标不变（存活非狼）；新增 `pending: 'wolf-vote'` / `'wolf-runoff'` 的候选集 |
| `init/deal` | 无改动（种子与发牌不变） |

### 3.3 编排 / AI / selfplay

| 组件 | 改动 |
|---|---|
| `orchestrator.ts` | `nextActor` 在 `NIGHT_WOLVES` / `NIGHT_WOLF_RUNOFF` 返回**尚未投票**的狼（按席位序）；`isPlayerPhase` 已含夜间，玩家自己的狼票走输入通道 |
| `playerAction` | 新增狼票输入（目标座位），与投票复用同一套「文本 → target」解析 |
| `scriptedAgent` | 狼票从 `legalTargets` 里按确定性轮转挑选（不投队友） |
| `selfplay` | 不需要改结构；批次的 `events` 会变长（多出投票事件） |

### 3.4 界面

- `NightAction` 的 `kill` 分支改为「狼队投票」：显示**当前票型**（谁投了谁）与自己的投票按钮；平票重投时只显示并列者，且**没有弃权**。
- 讨论阶段与投票阶段分开：讨论看到队友的话，投票看到票型。
- 死亡/终局不再受影响。

### 3.5 测试

- 引擎：三狼各一票 → 结算；2:1 分出；1:1:1 → 重投；重投再平 → 按裁定；死狼不投票；投队友被拒；非狼席位不能投狼票。
- 编排：玩家是狼时被逐票询问；AI 票与玩家票合并。
- 界面：票型渲染、重投候选、无弃权。
- e2e：狼夜从「讨论 → 投票 → 平票重投 → 天亮」全流程。
- selfplay：100 局冒烟仍能跑完；`summary.json` 字段不变。

## 4. 被否决的替代方案

| 方案 | 为什么否决 |
|---|---|
| 保持「第一个出手的狼决定」 | 用户明确反对：真人局里等于把三人共同决定交给一个人 |
| 讨论后由**队长**（固定席位）决定 | 规则上多一个身份；且队长仍可能忽略队友意见，争议没解决 |
| 随机在合法目标里选 | 与「玩家在打牌」的体验相悖；也让复盘没有可解释的决策链 |
| 平票就不刀（夜间无死亡） | 规则上可行，但会让狼队故意平票拖夜；是否采用取决于 §6 的裁定 |

## 5. 建议策略

1. 本变更**立即实施**（阻塞「合不合理」的试玩判断，且越晚改动越贵）。
2. 新增 **RFC-017** 承载实现；RFC-001/003/010 标 `Spec changed`。
3. 引擎改动尽量复用现有「提交 → 拒绝 → 相位推进」机制，不引入新的结算顺序。
4. 先补 `TEST-STRATEGY.md` 的 RFC-017 小节，再写代码（硬规则 3）。

## 6. 开放问题（需要用户拍板）

| ID | 问题 | 候选 |
|---|---|---|
| Q-011-1 | 重投**仍然平票**时怎么办？ | (a) 今晚空刀（无人出局）· (b) 并列者再投一轮（可能反复）· (c) 在并列者里随机 |
| Q-011-2 | 三狼投票时，**玩家自己的票**要不要在投票前看到队友投了谁？ | (a) 投票前只能看到讨论，投完才揭示票型（更像真实牌桌）· (b) 实时看到票型 |

## 7. 结论

**建议接受**。规则上新增 RUL-13、实现上新增 RFC-017，并同步改 RFC-001/003/010 的契约描述。

**Decision: accepted（2026-11-20）** —— 用户选择：

- 重投仍平票：**并列者继续投，直到分出结果**。实现上必须有终止条件，因此补了
  「重投未收缩时取并列者中席位最小者」的兜底（记为 RUL-13 的一部分）。
- 票型：**实时可见**（狼队投票阶段显示当前票型）。
- 变更本身：**按此方案做**。

**执行记录**：`RULES.md` 新增 RUL-13；`PRD.md` 新增 D46；RFC-001/003/010 标 `Spec changed`；
新增 `RFCs/RFC-017-wolf-team-vote.md`（Implemented）；`TEST-STRATEGY.md` 增加 RFC-017 小节；
引擎、投影、编排、界面与测试同批落地。
