# 变更请求 007 · 同步「同时达成」的旧表述（C-29）

> 提出日期：2026-11-18
> 提出人：RFC-003 Round 4 评审（C-29，非阻塞 RFC-003、**阻塞 RFC-004**）
> 评估基线：`RULES.md` v1.2（RUL-1 / RUL-12）、`PRD.md` v0.4（RA-1）、`RFCs/RFC-004`、`RFCS.md` v2.24
> 决策状态：**待用户确认**

---

## 0. 总体判断

这不是需求变化，是**五处旧表述没跟上 RUL-12**。

背景：Round 3 之前，`RULES.md` 的 RUL-1 声称「两阵营同时达成本身不可能发生」——理由是「狼胜成立瞬间对局已结束，猎人没机会开枪」。那条论证只覆盖**猎人开枪**这一种触发源，而 C-27 发现的**同一批夜间死亡**（最后一名神被刀 + 最后一只狼被毒）是**合法路径**，它证明了「不可能」是错的。

Round 3 已经补了 **RUL-12「狼刀在先」**，代码（`win.ts`）也按 RUL-12 跑对了。但**下游文字还停留在旧断言上**——尤其 `FEATURES.md` F6 AC-4 明写「因此两阵营不可能同时达成」，而 RFC-004 是下一个要实现的 RFC，它的 §2.6 整节标题就是「不存在『同时达成』」。

**风险不是「文档不好看」**：RFC-004 的白天判定要复用 `checkWin`。若实现者照着 §2.6 与 F6 AC-4 的「不可能」去写，很可能加一个「理论上不会发生」的断言——那正好会把 RUL-12 的合法路径判成 bug。

**代码零改动**：评审明确「代码按 PRD + RUL-12 是对的，不要改 `win.ts`」。本 CR 只改文字。

## 2. 冲突检查

对照 `RULES.md` 全文：

| 规则 | 是否冲突 | 说明 |
|---|---|---|
| **RUL-1** 正文 | **不冲突** | 「死亡结算完成后立即判一次；已分出胜负则死亡触发技能不结算」——判定**时机**没有变。变的是「同一时刻两个条件都成立时判谁」，那是 RUL-12 |
| **RUL-1** 的依据句 | **冲突** | 最后一句「这一条同时消除了『两阵营同时达成』的歧义」——被 C-27 推翻。要改成「只消除**猎人开枪**这一种的同时达成；同批死亡的情形由 RUL-12 裁决」 |
| **RUL-5** | 不冲突 | 只看存活，不看死因；新表述沿用 |
| **RUL-12** | 不冲突 | 它是新表述的**依据** |
| **ARCH-11** | **满足** | 旧表述等于宣称「这个分支不存在」，而它存在；改完后分支有明确裁决 |

对照 `PRD.md` 的 Decisions 与 out-of-scope：

- **RA-1 / RA-6** 都是**提问**，不是决定。RUL-12 回答了 RA-1；RA-6（猎人开枪触发源）由 RUL-1 原有论证覆盖，不受影响。
- 没有 PRD 决定被推翻。

对照 `changes/` 里已接受的决定：

- **CR-002** 曾把「同时达成 → 平局」反转成「胜负先于技能」，并据此移除了 `draw`。**本 CR 不恢复平局**：同时达成时仍有唯一答案（wolf 胜），只是答案来自 RUL-12 而不是「不可能发生」。CR-002 的结论（无平局）继续成立。

## 3. 逐处改动

### 3.1 `FEATURES.md:67`（F6 AC-4）

**现在**（尾句）：

> 4) 死亡结算完成后**立即判定胜负**；已分出胜负时死亡触发技能不再结算，因此两阵营不可能同时达成（RUL-1）

**改为**：

> 4) 死亡结算完成后**立即判定胜负**；已分出胜负时死亡触发技能不再结算（RUL-1）。**同一批夜间死亡可能同时满足两阵营条件**（如最后一名神被刀 + 最后一只狼被毒），此时按 RUL-12「狼刀在先」判 wolf 胜

### 3.2 `RULES.md:233`（RUL-1 的依据）

**现在**（尾句）：

> 这一条同时消除了"两阵营同时达成"的歧义：狼胜成立的瞬间对局已结束，不存在后续开枪

**改为**：

> 这一条消除的是**死亡触发技能**带来的同时达成（狼胜成立的瞬间对局已结束，猎人没有开枪机会）。**同一批夜间死亡**仍可能同时满足两阵营条件，那由 RUL-12「狼刀在先」裁决——它只决定同时成立时判谁，不改变本条规定判定时机

（RUL-1 的**规则正文不动**。）

### 3.3 `RFCS.md` 的 C-6 与 OQ-C6 两行

两行都由「**同时达成不可能发生**」改为「**猎人开枪这一种同时达成不可能；同批死亡由 RUL-12 裁决**」，并追加指针：`C-27 发现合法路径 → RUL-12（CHANGE-REQUEST-006）`。

保留原结论（无平局、`draw` 已移除），避免读者误以为 CR-002 被推翻。

### 3.4 `RFCs/RFC-004` §2.6（标题与正文）

**现在**：标题「不存在「同时达成」，也没有平局」。

**改为**：「**没有平局；同一批死亡可能同时达成，按 RUL-12 判 wolf 胜**」，正文补一段：

> 白天放逐不会造成「好人侧被清空」，所以 **RFC-004 的判定路径上不存在同时达成**。这条只约束夜间：`checkWin` 的 wolf 侧条件优先（RUL-12），白天复用同一个谓词时结果是唯一的。

（RFC-004 自己不需要实现新逻辑，只是不能照抄「不可能」并加断言。）

### 3.5 `RFCs/RFC-004` 的 Q-004-4

**现在**：

> ~~同时达成判平局~~ | **已关闭**：RUL-1 反转后该情形不存在（`CHANGE-REQUEST-002`）

**改为**：

> ~~同时达成判平局~~ | **已关闭（结论不变）**：不判平局。夜间同批死亡同时达成时按 **RUL-12** 判 wolf 胜（`CHANGE-REQUEST-006`）；`draw` 分支与 RUL-10 均已移除（`CHANGE-REQUEST-002`）

### 3.6 `RFCs/RFC-004` 的 Rules 头

`**Rules**: ... RUL-1, RUL-2, RUL-9, RUL-10` → 追加 **RUL-12**。

## 4. 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 把「同时达成」重新定义成不可能（例如让毒药在狼胜后失效） | 那要改 `resolveNight` 的语义、推翻 RUL-11 与真实规则；而且 C-27 的场景是**同时结算**，没有「之后」 |
| 只改 `RULES.md`，不动 FEATURES / RFC-004 | RFC-004 是下一个开工的 RFC，它的 §2.6 与 F6 AC-4 正是实现者要读的东西。留着旧断言 = 让实现者按错的规格写代码 |
| 恢复平局分支 | CR-002 已裁决移除 `draw`，且真实规则同样判 wolf 胜；恢复平局等于同时推翻两条 |
| 改代码去迁就旧文字 | 评审明确「代码是对的，不要改 `win.ts`」；改代码就等于把真实规则判错 |

## 5. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 只改标题、正文还说「不可能」 | 读者拿到互相矛盾的规格 | 逐处给出**改动前后原文**（§3），落地后 grep `同时达成` 复查 |
| 有人把「RUL-12」误读成「改判定时机」 | 后续 RFC 可能把 `checkWin` 提前调用 | RUL-12 与 RFC-004 §2.6 的措辞都明写「只决定同时成立时判谁，不改变判定时机」 |
| RFC-004 的 Status 被误改 | 它还没开工（`Not started`），不该出现 `Spec changed` | 本 CR 不动任何 RFC 的 Status：RFC-003 是 `Reviewed` 且其 AC 未变；RFC-004 是 `Not started` |
