# 变更请求 004 · 派生状态放哪（C-18）与 `DAY_VOTE_RESOLVE` 的归属（C-19）

> 提出日期：2026-11-17
> 提出人：RFC-001 Round 3 评审（阻塞项 F3 / C-18；非阻塞项 F4 / C-19）
> 评估基线：`RFCs/RFC-001` §2.3 `GameState`、`RFC-002` §2.1 / §2.4、`RFC-003` §2.5、`RFC-004` §2.2 / §2.3、`RFC-005` §2.2
> 决策状态：**2 项全部由用户裁决并落地**（2026-11-17）

---

## 0. 总体判断

**C-18 是真缺口，不是措辞问题。** RFC-002 的 `step(state, action)` 只接收状态与动作，看不到事件历史；而 RFC-003/004/005 明确要求「药水位、发言 cursor、票箱、夜聊提交」由事件流推导。`GameState` 只有八个字段，一个都没有。于是下一个实现者会撞上「在 `step` 里判不出这瓶药是否已用」这种问题——而那不是一个实现细节，它决定 `GameState` 要不要扩、`step` 要不要换签名。

**C-19 是措辞问题，但会变成实现问题。** RFC-004 写「全部提交后进入 `DAY_VOTE_RESOLVE`」，而 14 个 `Phase` 里没有它；RFC-002 的结算点叫 `VOTE_RESOLVE`。不裁决就会在 RFC-004 里多出第 15 个阶段名。

两项都不改需求：PRD 的 FR / NFR、FEATURES、RULES 一条都不动（方案 A 不触碰 `ARCH-4`，这是它相对方案 B 的主要优势）。

## 2. C-18 · 派生状态放哪

### 2.1 冲突的具体位置

| 来源 | 原文 | 与 `step(state, action)` 的关系 |
|---|---|---|
| RFC-003 §2.5 | 「药水是否已用**从事件流推导**，不在 `state` 里加布尔位」 | `step` 看不到事件流，判不出 |
| RFC-003 §2.5 | 「查验结果与药水位**不能只写进 `state`**，否则 `replay(events)` 无法重建它们」 | 这句其实**允许**写进 state，只要可重建——与上一句自相矛盾 |
| RFC-004 §2.2 | `DAY_SPEECH` 的 `cursor` 记录下一位发言者 | `cursor` 不在 `GameState` 里 |
| RFC-004 §2.3 | 「票箱从 `VOTE_CAST` 事件推导，不在 `state` 里另存一份可变 `Map`（ARCH-3 禁止 `Map`）」 | 理由说的是「禁止 `Map`」，而普通数组并不违反 `ARCH-3`；结论被理由带偏 |
| RFC-005 §2.2 | 「已提交夜聊的席位**记录在状态里**，由 `WOLF_CHAT_POSTED` 事件推导」 | 这条已经是方案 A 的写法 |

第五行是关键证据：RFC-005 写对了，前三处写成了「不许进 state」。**三个 RFC 对同一件事有三种说法，而 RFC-002 的签名只与其中一种相容。**

### 2.2 方案 A（推荐）· 派生字段合法，但只由 `applyEvent` 写

**规则**（写进 RFC-001 §2.3）：

> `GameState` 可以包含由事件折叠出的**派生字段**（发言 cursor、票箱、药水位、夜聊提交集合等）。它们必须满足两条：
> 1. **只由 `applyEvent` 写入**，且写入逻辑必须能从事件 payload 完整重算，不得依赖调用时的外部信息；
> 2. 它们是事件的**物化视图**，不是第二权威。两者冲突时以事件流为准（`DATA-3`）。
>
> 因此「不在 `state` 里另存」的准确含义是**不在 `state` 里另存不可重建的副本**。

**各字段的归属**：RFC-001 不预设这些字段的形状，由引入对应事件的 RFC 一并添加字段与 `applyEvent` 分支（RFC-003 加药水位，RFC-004 加 cursor 与票箱，RFC-005 加夜聊提交集合）。RFC-001 只定规则。

**配套**：
- RFC-002 §2.1 加一句：`applyEvent` 是派生字段的唯一写入口，`replay` 必须重建全部派生字段。
- RFC-003 §2.5 / RFC-004 §2.3 的「不在 `state` 里加布尔位」「不在 `state` 里另存一份可变 Map」改成「不在 `state` 里另存**不可重建**的副本」。
- TEST-STRATEGY 的 RFC-002 小节补一条：**同一事件流 `replay` 后，`step` 用重建状态做出的判定与原始运行逐项一致**（评审明确要求）。

**优点**：`step` 保持 `O(1)` 与 `ARCH-4` 的字面签名同时成立；`replay` 的一致性由既有 `DATA-3` 保证；不需要改 RULES。
**代价**：`GameState` 会随 003/004/005 长大，需要「只由 `applyEvent` 写」这条纪律，靠 code review 与 replay 一致性测试守。

### 2.3 方案 B · `step(state, events, action)`

**做法**：`step` 接收事件历史，判药水位 / cursor / 票箱时现场折叠。

**优点**：`GameState` 保持最小，派生数据永远只有一份来源（事件流）。
**代价（三项，逐条）**：
1. **要改 RULES**：`ARCH-4` 写的是 `reduce(state, action) => state`。方案 B 让 `reduce` 也不得不多带事件参数，等于改一条工程规则——而 RULES 的权威高于 RFC，改它的成本与影响面都远大于改 RFC。
2. **`step` 从 O(1) 变成 O(N)**：每个动作都要重新折叠整条事件流。一局几百个事件、AI 每回合若干动作，重复计算且没有缓存位置（缓存又回到方案 A 的「派生字段」）。
3. **纯函数验收变弱**：`step` 的行为取决于整条历史，而不是「状态 + 动作」，测试要从「构造一个状态」退化成「构造一条事件流」。

## 3. C-19 · `DAY_VOTE_RESOLVE` 的归属

| 现状 | 冲突 |
|---|---|
| RFC-004 §2.3：「全部提交后进入 `DAY_VOTE_RESOLVE`」 | 14 个 `Phase` 里没有它（RFC-001 AC-5 明确是 14 个） |
| RFC-002 §2.4：`ResolutionPoint = 'NIGHT_RESOLVE' \| 'VOTE_RESOLVE' \| 'DEATH_RESOLVE' \| 'WIN_CHECK'` | 结算点叫 `VOTE_RESOLVE` |

**方案 1（推荐）· 它是结算点，不是阶段**

`DAY_VOTE_RESOLVE` 是「所有票交齐 → 公开票型」这一瞬间的结算动作，不是玩家可停留的状态，因此不该占一个 `Phase`。改成：

> 全部提交后在 `DAY_VOTE` 阶段内触发结算点 **`VOTE_RESOLVE`**，产出一条公开的 `VOTE_REVEALED` 事件……

`Phase` 保持 14 个，AC-5 不变，RFC-002 的 `ResolutionPoint` 不变。

**方案 2 · 真的加一个第 15 阶段**

需要同时改 RFC-001 AC-5（14 → 15）、`Phase` 断言测试、`PHASES` 数组、RFC-004 的状态机表，并让 `VOTE_RESOLVE` 从一个结算点变成阶段名。**为一个不承载玩家输入的过渡瞬间改冻结的契约，不建议。**

## 4. 冲突检查

### 4.1 与 RULES.md

| 规则 | 方案 A | 方案 B |
|---|---|---|
| **ARCH-3** 状态是纯数据（无 `Map`/`Set`/`Date`/类实例） | 派生字段用数组 / 普通对象即满足 | 同 |
| **ARCH-4** `reduce(state, action) => state` | 不变 | **冲突**，必须改规则 |
| **ARCH-5** 先产效果再统一应用 | 无关 | 无关 |
| **DATA-3** `replay(events) === state` | 派生字段由 `applyEvent` 折叠 ⇒ 天然满足；要在 RFC-002 写明 | 天然满足 |
| **DATA-4 / DATA-5** PRNG 与 `Math.random` | 无关 | 无关 |

**方案 A 无规则冲突；方案 B 触碰 `ARCH-4`。**

### 4.2 与 PRD / FEATURES / 既有决策

- PRD **NFR-2**「状态可完整序列化为事件流并重放」——方案 A 直接服务这条。
- PRD **D43**「v1 预留四个扩展点，事后补要重写结算层与状态层」——方案 A 让状态层可扩展，正是 D43 的意图。
- **C-15 / C-16 / C-17**（事件形状）互不重叠。
- **C-13 / C-14**（RULES 措辞）无关；本 CR **不改 RULES**，也不解决 C-13 / C-14。
- 已接受的 **CR-001 / 002 / 003** 无一条被推翻。

### 4.3 与 `RFCS.md` 的登记

**C-18 / C-19** 已由 Round 3 评审登记。裁决后要改成「已解决 + 采用了哪种方案」，**不删除**——它们记录了「为什么当年有三种说法」。

## 6. 风险评估

| 风险 | 影响 | 缓解 |
|---|---|---|
| 方案 A 的纪律靠人守：「只由 `applyEvent` 写」没有类型强制 | 某人若在 `step` 里直接改派生字段，`replay` 就会与实时运行分叉 | 用评审要求的 replay 一致性测试守；RFC-002 的 AC 里明确这条 |
| `GameState` 随 RFC 长大 | 单文件/单接口膨胀 | 派生字段按「夜间 / 白天 / 夜聊」分组，由各自的 RFC 定义并说明来源 |
| C-19 改措辞后，实现者仍可能想加阶段 | 又多一个未裁决阶段名 | RFC-004 明确写「`VOTE_RESOLVE` 是结算点，不是 `Phase`」，并在 RFC-002 §2.4 的 `ResolutionPoint` 旁交叉引用 |

**不做的风险**：RFC-002 开工时实现者必须先做一次架构裁决（而且很可能选错方向、在 `step` 里偷偷改状态），等发现 `replay` 不一致时，返工范围是「引擎 + 重放 + 三个角色 RFC」。
