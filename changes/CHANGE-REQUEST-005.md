# 变更请求 005 · 把「毒药优先」写入 RULES（RUL-11）

> 提出日期：2026-11-18
> 提出人：RFC-003 Round 2 评审（阻塞项 B-R2-2）
> 评估基线：`RULES.md` §6（RUL-1 ~ RUL-10）、`RFCs/RFC-003` §2.3 / §9.1
> 决策状态：**已接受并落地**（决策来自用户在 RFC-003 Round 1 的裁决）

---

## 0. 总体判断

这不是需求变化，是**规则裁决的落榜**。

起因：RFC-003 实现时发现 `RULES.md` §6 没有裁决「狼刀目标与毒药目标是同一席位」的情形。Round 1 评审时我把它作为 C-24 提给你，你选了**毒药优先**（猎人因此不开枪）。问题在于——**这条裁决只写进了 RFC-003 §9 的 Implementation Notes**，而 `RULES.md` 是权威（`PRD > FEATURES > RULES > RFC`）。

Round 2 评审把这一点抓出来了："不要再把 §9 当作批准证据"。RFC 的实现说明是**证据记录**，不是**规则**；下一个人读 RULES §6 时找不到这条，就会在 RFC-004 或 RFC-005 里重新撞一次。

**本 CR 做的事**：把已经做出的裁决写进它该在的地方，并同步受影响的引用。

## 2. 逐项说明

### R-1 · RUL-11 的措辞与理由

**裁决内容**（写入 RULES §6）：

> **RUL-11** | 通用 | 狼刀与毒药指向**同一席位**时，该席位只出局一次，**死因记为毒药**；若该席位是 hunter，则**不开枪** | 死亡集合是「出局者」而不是「出局原因」，同一人多因只算一次；死因取毒药是因为 `FR-17` 的本意是「被毒杀的人拿不走开枪」，而 witch 明确选中了这个目标——把她的效果判成失效，等于让「毒狼刀口」变成一步废棋

**为什么「同一人只出局一次」是必须的，不是可选项**：实现层面，`applyPlayerDied` 把「对已出局座位再次 `PLAYER_DIED`」当作数据损坏（`InvalidEventStreamError`）。修复前，女巫毒狼刀目标是**合法 action 却让引擎崩溃**（评审 Round 1 的 B1）。归并是消除崩溃的唯一方式。

**为什么死因取毒药而不是狼刀**（另一选项的实际后果）：
- 取毒药 → 女巫多了一个「静默掉 hunter」的战术选择；被毒的人一律拿不走死亡触发技能（与 `FR-17` 一致）。
- 取狼刀 → 女巫花一瓶药、对已被刀的人下毒**没有任何效果**；「毒杀剥夺开枪」这条规则出现例外。

用户选了前者。

### 2.1 与既有裁决的关系

- 与 **RUL-1**（胜负先于死亡触发技能）无冲突：RUL-11 只决定「死因」，判定时机不变。
- 与 **RUL-3**（每夜至多一种药）无冲突：狼刀与毒药来自不同来源，`RUL-3` 约束的是 witch 一侧。
- 与 **RUL-5**（屠边只看存活不看死因）无冲突：RUL-11 决定的是「触发技能与否」，屠边判定仍然只看 `alive`。
- 与 **RUL-8**（解药先于击杀）互补：解药抵消狼刀；若同一目标还被毒，毒药仍然生效——这正是 §2.3 的「解药命中刀口、毒药仍然生效」路径。

## 3. 冲突检查

### 3.1 与 RULES.md 自身

- §4 的「规则索引」把 RUL 计为 10 条、总计 75 条 → 需改为 11 / 76。
- §6 的引导句写「RA-1 ~ RA-10 的正式答案」→ 需说明追加了 RUL-11。
- 规则 ID 是**只增不改**的（`RULES.md` 文件头），所以新增用下一个编号 `RUL-11`，不改动 RUL-1 ~ RUL-10 的任何一条。

### 3.2 与 PRD / FEATURES / 既有 CR

- PRD **FR-17**（严格规则集：女巫不可自救、被毒杀者不能开枪）是本裁决的依据之一，不冲突。
- FEATURES **F8 AC-4**（被毒杀的猎人不能开枪）同样支持「毒药优先」。
- 已接受的 **CR-001 ~ CR-004** 与本 CR 无重叠。**CR-002** 曾修订 RUL-1 / RUL-2 / RUL-10——本 CR 与它同属「规则裁决落榜」，不改动它做过的事。

### 3.3 与 RFC

- `RFCs/RFC-003` §2.3 的第 3–6 步需要引用 RUL-11（否则读者仍看不到依据）。
- `RFCs/RFC-004` 的 `DAY_STARTED.diedLastNight` 依赖死亡结算顺序——RUL-11 不说顺序，只说「同一人只算一次」，所以不影响它；顺序由 RFC-003 §2.3 的步骤（狼刀先、毒药后）决定，见 C-26。

## 5. 风险评估

| 风险 | 影响 | 缓解 |
|---|---|---|
| 只改 RULES、忘了同步 RFC-003 的引用 | 读者在两处看到不同的措辞 | 落地清单第 5–6 项 |
| 将来 RFC-005 引入第三种死因（如自曝连带） | RUL-11 只覆盖两源，新组合无人裁决 | RFC-005 开工时若出现新组合，**新增 RUL 而不是扩写 RUL-11**（只增不改） |
| 「毒药优先」改变 hunter 的预期 | 玩家可能觉得被刀了却没开枪很奇怪 | 这是明确裁决的结果；复盘的事件流里 `PLAYER_DIED.cause === 'poison'` 可解释 |

**不做的风险**：Round 2 评审已经把它列为阻塞（B-R2-2）；RULES 缺这条，RFC-004 在处理 `diedLastNight` 时可能自行发明一套。

## 6. 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 把该情形改成「显式未裁决错误」（`ARCH-11`） | 它会让女巫毒狼刀目标变成**引擎主动抛错**——从「崩溃」变成「设计上的拒绝」，但这仍然是一个合法操作被拒绝。而且我们已经知道正确答案了，没必要保留一个空洞 |
| 只在 RFC-003 里写，不动 RULES | 正是 Round 2 抓到的 B-R2-2：RFC 的实现说明不是规则，下一个人读 RULES 找不到依据 |
| 扩写 RUL-3 或 RUL-8 | 规则 ID 只增不改；而且 RUL-3 说的是「每夜至多一种药」、RUL-8 说的是「解药先于击杀」，塞进去会让每条规则指代不清 |

---

## 7. 决策来源

**用户在 RFC-003 Round 1 的裁决**中选择了「毒药优先：猎人不开枪」（另一选项是「狼刀优先：猎人开枪」）。本 CR 不重新征询，因为问题与选项都没有变化——它只是把那个答案写进 `RULES.md`。
