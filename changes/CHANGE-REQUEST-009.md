# 变更请求 009 · 修正 AC-13 的「释放」措辞（C-61）

> 提出日期：2026-11-19
> 提出人：RFC-008 多轮评审（C-61，阻塞 RFC-008 的 `Reviewed`）
> 评估基线：`RFCs/RFC-008` §2.5 / §8 / AC-13、`PRD` NFR-17、`FEATURES` F37
> 决策状态：**待用户裁决**

---

## 0. 用牌桌的话说

一局打完之后，服务器为了让内存不越堆越多，会把这局的**完整过程记录**（每一句话、每一张票、每一步动作）删掉，只留一条「这局打完了」的索引。

RFC-008 的验收标准第 13 条说：「**释放后再取这局，内部重新 replay 得到同一状态**」。

问题是：**过程记录都删了，就没法「重新 replay」**——就像把一局牌的记谱纸烧了，却要求复盘出同一局牌。

所以现在代码按「删掉过程记录后，这局取出来是 410（已释放）」实现，并在测试里如实断言「无法重建」。但**验收标准的原话与这个实现相反**，评审因此不放行。

**这不是代码 bug，是一句话没写清楚。** 需要你定的是：这句话该改成什么。

## 1. 冲突在哪

| 位置 | 说的是什么 |
|---|---|
| RFC-008 §2.5 | 「`finished` 后 `GameState` 不再缓存；保留最近 3 局的完整 `events`，更早的只保留 `snapshot`」 |
| RFC-008 AC-13 | 「释放后再取该局，内部重新 `replay` 得到同一状态」 |
| 实现（D-5） | 释放 = 清空 `events`；此后 `GET` 返回 `410 GAME_EXPIRED`；`stateOf` 会抛错 |

「释放」在这个 RFC 里被当成两件事用：**释放缓存的状态**（合理，AC-13 想说的应该是这个）与**释放事件流**（§2.5 的做法）。两者不可能同时成立。

## 2. 候选措辞

### 方案 A（推荐）· AC-13 改成两句话

> 13a. **未释放**的终局记录不缓存状态：每次取都用 `replay(events)` 重新计算；改掉 `events` 后结果必须跟着变。
> 13b. 已释放的对局取状态返回 `410 GAME_EXPIRED`；复盘由 RFC-014 的快照承担。

**理由**：与 §2.5、D-5 的现有实现一致；`PRD` NFR-17 与 `FEATURES` F37 只要求「结束后可释放」，从没要求「释放后还能 replay」。改完之后，现有测试与实现不用动，只是把话说明白。

### 方案 B · 释放时保留一份压缩快照

> 13. 释放事件流时生成 `snapshot`；`GET` 仍返回该快照重建出的终局状态。

**代价**：`snapshot` 的生成属于 RFC-014（本 RFC 只留字段）。选 B 意味着把 RFC-014 的一部分提前到本 RFC，或者让 AC-13 悬空到 014 落地。

### 方案 C · 把 AC-13 移出本 RFC

> 13. （移交 RFC-014）释放与快照的关系由 RFC-014 定义。

**代价**：本 RFC 的 AC 就少一条，而「不缓存状态」这条性能约束没有归宿。

## 3. 权威检查

| 产物 | 是否要求「释放后还能 replay」 | 结论 |
|---|---|---|
| `PRD` NFR-17 | 否，只要求「对局结束后可释放」 | 不冲突 |
| `FEATURES` F37 | 否，只要求「结束后的对局可被清理」 | 不冲突 |
| `FEATURES` F35 | 只要求「对局中刷新恢复」 | 不冲突 |
| `RFC-008` §2.5 | 释放 = 保留 3 局完整事件，更早的只留快照 | 与 AC-13 原文冲突 |

按权威顺序，没有更高的产物要求「释放后还能 replay」，所以**改 AC-13 的措辞**是正确的方向，不需要改 PRD/FEATURES。
